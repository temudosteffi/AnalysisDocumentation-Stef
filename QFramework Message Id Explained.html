QFramework Message IDs — What They Are, How They're Chosen, What They Return

Plain-English answers to three questions about the QEnterprise capitation flow, each backed by code in mms-cms-cef/components/QFrame and the capitation agent. Nothing is assumed.

Q1 · Member or transaction? The 3 layers of identity Q2 · Which ID goes to the hub? Q3 · One record or a set? Cheat sheet

Q1 — Are these message IDs assigned to a member, or to a transaction?

A transaction (a unit of work), not a member. A QEnterprise message ID (QISMessageId = the Message Store key message.messageid, a char(36) value) identifies one transaction message — a serialized QFrameTransactionType. Member information (memid, enrollid, dob…) is data carried inside the message, never the message's identity.

The proof is in what the message deserializes into. The execution engine turns the message body into a transaction object and runs it by its LogType — there is no member key involved in identifying the message:

QFrame/Infrastructure/Common/Src/QCSI Process Execution/MessageProcessorEngine.cs
m_transactionMessage = (QFrameTransactionType) CUtility.GetObject(tranMsg, typeof(QFrameTransactionType));
m_processManager.Initialize(session, m_transactionMessage.Process.LogType);   // identified by transaction + LogType
host.Execute(m_transactionMessage, session);

For capitation, the first message is a program-level submit (CapSubmitRequestMessageType) — it describes a Program and capitation settings, not a person:

components/QNXT/ASCs/Capitation/Src/QCSI ASC CapitationSetup/CapProgramAgent.cs
CapSubmitRequestMessageType reqInfo =
    (CapSubmitRequestMessageType)CUtility.GetObject(message, typeof(CapSubmitRequestMessageType));
// reqInfo.Program.Id, reqInfo.Capitation.* … → a program run, not a member
cap.BuildProgramCapitation(message);

The three layers of identity (why this is confusing)

Capitation has three different “ids” at three levels. Only the top one is the QEnterprise message ID.

① Transaction message  QISMessageId — char(36)

The QEnterprise message. One per unit of work (e.g. a “Submit Program Capitation” request, LogType ADV_CAP_PROC). This is what the hub sends to an Execution Unit.
▼ the agent fans this out into…

② Provider messages  CapProviderRequestMessageType[]

One message per provider/affiliate. The agent builds a provider list and submits an array of these downstream — each becomes its own QEnterprise message with its own QISMessageId.
▼ which stage member-level rows into…

③ Enrollment work-items  capmessagequeue.messageid — a counter

One row per member enrollment (memid, enrollid, dob…). Here messageid is just a sequential number within a batch (a zint counter), paired with capmessagequeueid — not the QEnterprise GUID.

Each provider message is submitted back through QEnterprise by a proxy — confirming that a provider (work unit), not a member, becomes a message:

components/QNXT/ASCs/Capitation/Src/QCSI ASC CapitationSetup/CapProviderActivity.cs
CapProviderRequestMessageType[] provMessages = ConvertToProvMessages(dt, message, recondate, reviewdate, advreconrun);
Q.Proxy.CapProviderProxy myCap = new Q.Proxy.CapProviderProxy(this.Session);
myCap.ProcessMessage(provMessages);        // each provider → its own downstream message
Watch the name collision: the word “messageid” appears in two places with different meanings — the QEnterprise message.messageid (char(36), a transaction key) and the capitation capmessagequeue.messageid (a per-batch counter at the member/enrollment level). They are not the same thing.

Q2 — How is it decided which message ID is sent to the hub?

The ID is system-generated when the message is stored, and selection is by LogType + priority + ownership — not by business choice. A submitter/agent creates a message; it is written to the Message Store and gets its char(36) id automatically. From there, messages are handed out based on what type they are, their priority, and which server currently owns them.

2.1 The ID is minted by the database, not chosen

When a message is inserted, SQL Server returns the new id — the application never picks it:

QFrame/Infrastructure/Common/Src/QCSI Message Store/StoreMessage.cs
sql = "Insert INTO message (messagetext) output inserted.messageid VALUES(@messagetext)";  // DB mints the id
messageid = DbUtil.ExecuteScalar(paramoj, sql);
// then a MessageHeader row records StateId = Queued(0), LogType, Priority, etc.

2.2 Which queued messages get picked — priority, type, ownership

A server claims a batch of the oldest/highest-priority unclaimed messages whose LogType it is mapped to handle, and stamps them with its own QnxtServerId. That claim is what decides “which ids go out next.”

QFrame/Infrastructure/Common/Src/QCSI Message Store/MessageStore.cs — MarkMessages()
"Update MessageHeader set QnxtServerid = @qnxtserverid, Stateid = @stateid, statechgdate = getdate() "
+ "where messageid in ("
+ "  Select top " + config.SelectBatchSize.IntegerValue + " mh.MessageId "
+ "  FROM MessageHeader mh INNER JOIN MessageMap mm ON mh.logtype = mm.logtype AND mm.templateid = @templateid "
+ "  WHERE QnxtServerid IN (@qnxtserverid, 0) AND stateid = 0 "      // 0 = Queued / unowned
+ "  order by mh.priority desc, mm.priority desc)";                  // ◀ priority decides the order

On the hub side, the choice of which EU receives a given id is then made purely by LogType match among active workers (round-robin, respecting each EU's limit):

.../Distribution Hub/MessagPort.cs
if (unit.AcceptedMessageTypeCol.ContainsKey(aMessage.LogType)) { foundEU = true; }   // LogType decides the EU
// ... round-robin across active EUs, skip any EU already at MaxOutstandingRequests ...
So the “decision” is three filters, not a manual pick: state = Queued(0) → LogType mapped to this server/EU → highest priority first. The id value itself is irrelevant to selection; it's just the key that rides along.

Q3 — When data is retrieved from a message ID, is it a single record or a set?

A single message record per id — but that one record's payload can describe many members, and the member-level work is deliberately processed in sets (batches of 500). One QISMessageId → exactly one row in the Message Store → one payload. The “set” appears inside the payload and at the enrollment-queue layer, not at the id lookup.

3.1 Fetch by one id returns exactly one record

The EU looks the id up directly; zero rows is an error, and it reads Rows[0] — a single record:

QFrame/Infrastructure/Common/Src/WindowsService/Execution Unit/MessagePort.cs — loadMessageObjectFromDB()
DataTable dt = QIS.MessageStore.TakeOwnershipOfMessageAndGetMessageInfo(msgId);   // key lookup by id
if (dt.Rows.Count == 0)
    throw new Exception("Message with id: " + msgId + " does not exist in message store");
return CQISMessageHelper.CreateFromDataRow(dt.Rows[0]);     // ◀ ONE row → one message/payload

3.2 …but one payload can represent many members, processed in sets of 500

A single provider-capitation message can cover tens of thousands of enrollments. Rather than handle 100,000+ at once, the capitation proc writes them into capmessagequeue in batches of 500 so the program can pull a “manageable set” at a time. The proc's own comment says exactly this:

components/db/mssql/plandata_parallel/StoredProcedure/dbo.spQ_BuildGlobalCapMessage.StoredProcedure.sql
--inserts cap messages for global enrollments into the capmessagequeue table
--where the cap program can retrieve a manageable set of messages instead of 100K+ at one time
DECLARE @batchsize zint = 500
...
-- a cursor walks every eligible ENROLLMENT (one row per member enrollment) …
OPEN BuildCapEnrollmentMessages
FETCH NEXT FROM BuildCapEnrollmentMessages INTO @Rank, @enrollid, @planid, @memid, ...
...
-- … and every 500 enrollments it rolls to a new detail id / batch
IF @batchmsgcount >= @batchsize + 1 AND @PreRank <> @Rank BEGIN ... SET @batchmsgcount = 1 END
Two different “reads,” two different shapes:
  • By QEnterprise message id → one record (one transaction/payload). TakeOwnershipOfMessageAndGetMessageInfo(id) returns a single row.
  • By the message service sweep / capitation queue → a set. MarkMessages claims TOP N messages; capmessagequeue holds enrollments in 500-row batches per capmessagequeueid.

Cheat sheet

QuestionShort answerKey evidence
Is a message ID per member or per transaction? Per transaction / unit of work. Member data lives inside the payload. QFrameTransactionType; CapSubmitRequestMessageType; CapProviderRequestMessageType[]
Who assigns the ID? SQL Server, on insert (output inserted.messageid), as a char(36) key. StoreMessage.InsertMessage()
How is it decided which ID goes out? state=Queued → LogType mapped to server/EU → highest priority first (plus round-robin & EU limits). Not a manual pick. MarkMessages(); AcceptedMessageTypeCol.ContainsKey(LogType)
Fetch by a given ID → one or many? One record (one payload). The payload may list many members. loadMessageObjectFromDB() → Rows[0]
Where does the “set” happen? At the sweep & the enrollment queue — TOP N claims and capmessagequeue batches of 500. MarkMessages (TOP N); spQ_BuildGlobalCapMessage (@batchsize=500)
In one line: a message ID names a transaction (not a member); it is database-generated and selected for dispatch by type + priority + ownership; looking it up returns one record, while the many members it affects are handled in batches of 500 downstream.
