1. Executive Summary

An exhaustive, scoped search of the workspace found no single artifact named or structured as a “36-Month Summary File Extract – MCP Capitation History” that emits all nine advertised columns (Amount Paid, Days Paid, Member Months, MCP Code, Provider ID, Service Location, County Group, Rate Cell, Service Month) across a rolling 36-month window. UNKNOWN

Instead, the advertised business description maps onto a family of capitation artifacts that all read the same QNXT/COTS capitation ledger in plandata_parallel (capvoucher + payment + enrollkeys + capitation). Two implementations carry the majority of the described fields:

  • SSIS flat-file extract — FINEX00038_PERM_FI_Capitation_Extract (Ohio.ETL). Produces a pipe/flat capitation detail file. CONFIRMED
  • SSRS report + stored procedure — FINRP00001L Capitation List / usp_FINRP00001L_Capitation_List (OH_FI_Reporting). Carries Service Month, Days Paid, Amount Paid, Provider ID, MCP Code, and the cap-rate (Rate Cell) key. CONFIRMED

Three of the nine advertised columns — Member Months, County Group, and the 36-month retention window — were not found as implemented logic anywhere in the searched repositories. UNKNOWN The most likely reading is that the “36-Month Summary” is a logical/actuarial reporting specification assembled downstream (EDW/actuarial), fed by these CEF capitation detail sources, rather than a discrete CEF extract job. INFERRED

8. Business Logic Analysis

  • Amount Paid = capitation voucher amount cv.capamount (and/or check-level payment.amountpaid). In the monthly MCO totals proc it is split by fund: WITH% funds → withhold, MONTHLY non-withhold → non-adjustment, otherwise adjustment. CONFIRMED usp_MonthlyCapitationPaymentCycleCHIPtoMCOTotals.sql:15-18
  • Days Paid = cv.daycount straight from the voucher (partial-month proration count). A daycount = 0 is business-flagged as a “Rate Change” adjustment. CONFIRMED usp_FINRP00001L_Capitation_List.sql:79, :92
  • Member Months — no calculation located. UNKNOWN Would normally be a COUNT of distinct member×cap-month rows; the nearest implemented concept is a distinct-member roster count. INFERRED
  • County Group — no derivation located on any capitation output. UNKNOWN Ohio rate-cell config carries MC_Group/MC_Region which could source it, but no join exists in the found extracts. INFERRED
  • Rate Cell — the cap-rate key cv.caprateid (linked to capitation.capid) drives it; selection of the rate cell happens upstream in the COTS capitation runtime (rate-cell selection Query 10794 → cCapFundAllocation). CONFIRMED usp_FINRP00001L_Capitation_List.sql:104; mms-cms-cef Custom "COTS Capitation Runtime — Full Table Read/Write Map":111,172
  • MCP Code — looked up from the member’s managed-care attribute value (memberattribute.thevalue where attributeid = MEMEX00040_MANAGED_CARE_ATTRIBUTEID). CONFIRMED

Calculation venue: overwhelmingly SQL (proc + SSIS OLE DB SqlCommand). No calculation of these measures occurs in SSRS expressions or .NET for these artifacts. INFERRED

9. Historical Retention Logic

No 36-month (or any fixed multi-month) retention/window logic was found in the capitation extracts or reports. UNKNOWN Both implementations are parameter-driven date ranges:

  • FINEX00038: WHERE pmt.paydate >= ? AND pmt.paydate < ? (SSIS parameters). CONFIRMED
  • FINRP00001L: WHERE p.checkprintdate BETWEEN @PaidBegDate AND @PaidEndDate. CONFIRMED usp_FINRP00001L_Capitation_List.sql (WHERE clause), :140 (CapType in ('RECON'))

Consequently the “36 months” is externally configurable at run time (whoever supplies the date parameters), not encoded in the code. There is no evidence of a hard-coded 3-year retention rule. INFERRED

15. Final Verdict

  1. What component generates the extract? No single component emits the exact 9-column / 36-month file. The closest real file-extract is the SSIS package FINEX00038_PERM_FI_Capitation_Extract (Ohio.ETL) writing PERM_FI_Capitation_Extract.txt; the closest report is FINRP00001L Capitation List (OH_FI_Reporting). CONFIRMED / composite INFERRED
  2. True purpose? To surface QNXT/COTS capitation payment history (voucher + check) per member/provider/rate for finance and CMS PERM reporting — not, as literally advertised, a purpose-built 36-month MCP summary file. INFERRED
  3. Which procedures/tables drive it? usp_FINRP00001L_Capitation_List and the FINEX00038 SqlCommand, over plandata_parallel: capvoucher, payment, enrollkeys, capitation, planprovinfo, memberattribute (+ Flexi..APDI, memberview). CONFIRMED
  4. How are Amount Paid, Days Paid, Member Months calculated? Amount Paid = capvoucher.capamount / payment.amountpaid; Days Paid = capvoucher.daycount (both CONFIRMED). Member Months = no implemented calculation found UNKNOWN.
  5. How are County Group and Rate Cell derived? Rate Cell = capvoucher.caprateid → capitation.capid, selected upstream by the COTS capitation runtime CONFIRMED. County Group = no derivation found on any capitation output UNKNOWN (candidate source MC_Group/MC_Region in MEMIM00065 rate-cell config, currently unjoined).
  6. Is the 36-month period configurable? There is no 36-month code; both artifacts use run-time date parameters, so the window is externally supplied/configurable rather than hard-coded. CONFIRMED (absence) / INFERRED (configurability).
  7. Who consumes the extract? FINEX00038 → CMS PERM capitation submission (“PERM_FI_Capitation”); FINRP00001L → finance/operations reconciliation users. INFERRED
  8. Code evidence proving each conclusion? See §12 Evidence Table (15 tagged rows with file:line).
Bottom line. The advertised “36-Month Summary File Extract – MCP Capitation History” is not implemented as a discrete artifact in the analyzed workspace. Six of nine fields are provably sourced from the plandata_parallel capitation ledger via FINEX00038 and FINRP00001L; Member Months, County Group, and the 36-month rolling window have no code evidence and are almost certainly assembled in a downstream EDW/actuarial layer outside this repository set. UNKNOWN / INFERRED
