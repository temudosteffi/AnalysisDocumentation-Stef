What Is Capitation? (Three Sentences)

Capitation is a fixed per-member-per-month (PMPM) payment that Ohio Medicaid makes to Managed Care Plans (MCPs) — Aetna, Buckeye, CareSource, Molina, Paramount, United Health — regardless of what services those plans actually deliver. Think of it as a "monthly payroll run for health plans": every month, the system decides which members are enrolled in which plans, looks up the rate each member's demographics command, and writes a check to each plan for the sum of its members' rates. The Ohio capitation system processes approximately 71 concurrent (program × period) runs per monthly cycle, touching 6+ databases and producing vouchers that flow through a general-ledger posting pipeline before the state releases funds.

Stage 0 — Run Invocation (How a Capitation Run Starts)

What is this? The trigger mechanism — how the system receives the instruction "calculate capitation for program X, period Y." Like pressing "Run Payroll" in a payroll system, except it fans out into dozens of parallel sub-runs.
What does it do? Accepts a run request (programs, cap date, recon date, retro months), fans it out into per-program messages, then per-provider messages, feeding the calculation pipeline.
What does it read/write? Reads dispatch config from PlanIntegration; writes run-state to processlogheader/processlogdetail.

Run Trigger

A capitation run is initiated either by a QNXT Administrator UI action ("Create Advanced Capitation Payments" wizard) or by a scheduled QFrame job-queue row. The wizard presents four operational modes E:

  • Create Months — calculate capitation for new period(s)
  • Reconcile Months — re-calculate for prior periods where retroactive changes occurred
  • Multiple Retroactive Months — reconcile up to 12 months of lookback in one pass
  • Reconcile Providers — re-run for specific provider(s) only

These modes generate the ~71 (program × period) runs clustered monthly. Each MCP (6–7 plans) × each retro month within the lookback window = dozens of runs. I

Stage 2 — Rate Sweep (Loading Capitation Rates)

What is this? Before the system can calculate how much to pay, it needs to load the rate tables — like loading a tax bracket table before computing withholding. The "rate sweep" is a batch ETL job that stages rate-cell data from reference files into the operational database.
What does it do? The MEMSW00013 SSIS package family loads rate-cell assignments into MemberCondition, mapping each member to a rate-cell code based on demographics (age, gender, region, coverage).
What does it read/write? Reads from ETLStageDB staging tables and HealthPAS_Common crosswalks; writes to MemberCondition in Plandata_Parallel.

Why "Sweep"

The term "sweep" means the ETL scans all enrolled members and assigns each to a rate cell based on their current demographics — a point-in-time staging of who-gets-what-rate. This is a pre-computation: it runs on its own schedule, separate from the cap engine, and deposits results into a shared table that the engine later reads. C

⚠ Known Rate-Load Defect

Three confirmed defects in the rate sweep (blocks 24-month capitation): C
  1. TRUNCATE Destroys History (H1): MEMSW00013_Standard_Stage_Receipt.dtsx executes TRUNCATE TABLE dbo.MEMSW00013_Standard_Stage before reload. The staging table DDL has NO effdate/termdate columns — only a point-in-time snapshot. Line ~5235
  2. Age-at-Load Collapses Effective-Dating (H2): The crosswalk join uses stg.Member_Age BETWEEN gap.Min_Age AND gap.Max_Age — this evaluates age at load time, not at each historical cap month. A member who ages from 24→26 over a 24-month lookback gets ALL months mapped to the age-26 rate cell.
  3. No TransactionOption: Zero packages have transaction wrapping — DELETEs/UPDATEs are non-atomic.
Impact: For single-period (monthly) runs the defect is invisible (current age = correct cell). For multi-month retroactive runs, members crossing age-bracket boundaries get the wrong rate for historical months.

Stage 4 — Cap Factor & Cap Term Configuration

What is this? A "cap factor" is an adjustment to the base rate — like a tax credit or surcharge applied per-member based on their characteristics. A "cap term" is the time-bounded configuration that says "this rate applies from date X to date Y." Together, they steer the final payment amount.
What does it do? Loads factor values (age/gender, benefit plan, condition, rate code) and cap terms; applies them to the base rate to compute the adjusted capitation amount.
What does it read/write? Reads capfactors, factorvalues, capterm from Plandata_Parallel; writes funddetail, funddetailadj.

Factor Types E

Product documentation describes two arithmetic modes:

  • Additive: a dollar amount added to the base (e.g., diabetes-condition factor adds $X)
  • Multiplicative: a rate multiplier on the base (e.g., 0.90 factor for single males 20–24 = 90% of base)

Factor value types: age/gender, benefit plan, benefit, condition, rate code. E

The Canonical Linkage Chain

C Rates are NOT reached directly from the MCO. The chain is:

MCO → (linked to) → Provider Contract → (through contract) → Capitation Table → Rate Cell

Each MCO is linked to a provider contract, and it is through that contract — not directly — that the MCO reaches its capitation rates. The provider contract is the indirection point.

Why This Indirection Matters

Because the rate is resolved via MCO → contract → cap table, two reconciliation triggers (Stage 3b #5 and #6) operate on the middle of the chain, re-pricing a member without the member or MCO changing at all:

  • Contract affiliation change (trigger #5) — the MCO→contract link changes → different rates
  • Capitation table change (trigger #6) — the cap table attached to the contract changes → different rates

Stage 6 — QFrame (The Calculation Engine)

What is this? QFrame is the master/worker compute grid that runs the actual capitation calculation. Think of it as a distributed calculator: a central hub dispatches work to application servers, which fan out to execution units, which each process batches of members. What does it do? Executes the 7-step inner pipeline for each member: build enrollment → build affiliations → calculate amount → allocate to funds → apply adjustments → store voucher → finalize payment.

The matched = possible Rule

A rate cell is valid if and only if matched = possible (the member satisfies EVERY criterion the cell defines). A cell requiring ZIP + gender + age where the member matches only ZIP + age → matched=3, possible=4 → invalid. Only perfect matches are accepted. C cCapFundAllocation.vb ~L382

Age Encoding — MONTHS, Not Years

CONFIRMED: Age is encoded in months. C
Evidence: The scoring SQL contains CASE WHEN 1 <> 1320 THEN 1 ELSE 0 END (a tautology constant for the possible clause). 1320 = 110 years × 12 months — the maximum representable age sentinel. Synthesis

1. End-to-End Plain-English Narrative (One Monthly Cap Run)

A monthly capitation run starts when the QNXT administrator (or a scheduled job) submits a request specifying which programs and which month to calculate. The CAPSubmit agent in PlanIntegration fans this request out into per-program messages using XSLT. Each per-program message hits CapData (which enriches it with rate/config from Plandata_Parallel) and then CAPGlobal or CapPcp (which builds a provider list and fans out again, per-provider). Now for each provider, the 7-step engine chain fires inside QFrame: cBuildCapEnrolls queries enrollment from Plandata_Parallel (data originally received from Accenture via MSMQ) and pre-allocates a paymentid from QCSIDB.IDSequence. cBuildCapAffils resolves which affiliate gets paid by joining members → contracts → cap tables in Plandata_Parallel. cBuildCapAmount calculates the base PMPM rate (reading premium invoices). cCapFundAllocation runs the 10-dimension scoring SQL against capterm in Plandata_Parallel, selects the winning rate cell (matched=possible rule, tie-break sort), and writes funddetail records. cCapFundAdjustment applies cap factors from capfactors/factorvalues/membercondition in Plandata_Parallel. cStoreCapVoucher writes capvoucher rows (one per member-cap-line) into Plandata_Parallel. cCapPayment sets payment.status='OPEN', creates a paycheck record. Then PostCap stored procs (fund allocation, split payment) run against Plandata_Parallel and write financial attributes to HealthPAS_Common.hpfin_FAAttributesCAP. The SSIS finance pipeline (hpfin_ClaimFundAllocation → hpfin_APInvoiceUpdate) picks up OPEN payments, creates AP invoices, and loads them into Flexi GL (TIVH/TIVD/APBH/PIPQ), setting status to INFLEXI. After Flexi confirms posting, Hpfin_ClaimResolution resolves the payment (INFLEXI→PAIDREMIT) and creates check history. Finally, ODM validates and releases the payment, OAKS authorizes state funds, and the 820 EDI agent generates premium payment advice to the MCPs via Edifecs/Deloitte.

3. The Retro/Reconciliation Mechanism

Why do the same scopes get re-processed? Six trigger types detect retroactive changes (Stage 3b): retro enrollment, MCO assignment change, enrollment-restriction change, cap term rate change, contract affiliation change, and cap table change. Each trigger that fires for a past period generates a reconciliation pass that re-vouchers the affected scope — writing positive or negative adjustment vouchers. This is why Ohio processes ~71 runs per monthly cycle: 6-7 MCPs × current month + retro lookback months × trigger-type combinations.

SurfaceWhereNatureWhat Goes Wrong
Stage 1b — Temporal-ConflictMCO-assignment resolutionData-value conflict (who gets paid)Two overlapping-period runs resolve the same member-month to different affiliates → different payees for the same member
Stage 7 — paymentid Collisioncapvoucher INSERTKey conflict (duplicate write refused)A restart/replay reuses the original paymentid → identical PK → INSERT rejected with PK violation error

Distinction: Stage 1b is about correctness (the wrong entity gets paid). Stage 7 is about durability (the write physically fails). Both are products of the retro/reconciliation mechanism but manifest differently.
