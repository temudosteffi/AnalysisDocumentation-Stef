PostCap_SplitPayment — Step-by-Step Data Workbook v2 — corrected

Stored procedure: dbo.PostCap_SplitPayment  •  Database: CA_Extensions  •  Runs immediately after the Capitation run

What changed from v1

  • Realistic CapVoucher granularity: CapVoucher is per member (enrollid) per fund, so a PaymentID has many rows — not 6. v1 wrongly showed one row per fund.
  • Real production FundIDs from PostCap_PreFundAllocate: weekly MSCDMQ… and withhold WITHLD….
  • "6" clarified: it is the maximum number of distinct funds (3 weekly + 3 withhold), reached only after the SUM(CAPAmount) GROUP BY FundID collapse — and only if all 6 funds are present.
  • Qualifying rule made explicit: a payment is split only if it has at least one weekly fund and at least one withhold fund.

What this procedure does (plain English)

After the Capitation run, a provider gets one Payment record whose amount is the lump sum of many per-member CapVoucher lines spread across several Funds. Some funds are meant to be paid out across weeks (weekly funds) and some are withheld. This procedure sums those lines per fund and splits the single payment into one Payment record per fund, so each week / withhold amount can be tracked and released separately.

  1. Read configuration — the 6 Funds, the Method, and each fund's week label.
  2. Find the payments to split — CAP payments that are OPEN, on the configured Method, that contain both weekly funds (Fund1‑3) and withhold funds (Fund4‑6).
  3. For each payment, SUM the many CapVoucher lines per fund → this is where the row count collapses to (up to) 6.
  4. Keep the first fund on the original PaymentID (just correct its amount).
  5. For every other fund, mint a new PaymentID and move that fund's CapVoucher / PayCheck / CapAdjustment rows to it. Funds 1‑3 → OPEN, Funds 4‑6 → WITHHOLD.

Row counts are not fixed. CapVoucher has one line per member per fund, so a real PaymentID often has dozens or hundreds of lines. The number of distinct funds is at most 6 (3 weekly + 3 withhold), and may be fewer depending on each member's rate-cell / cap-factor allocation.
Goal: collapse the many lines to one amount per fund, then turn the 1 payment into up to 6 payments — so each week can be released on its own schedule and withhold funds can be held back.

2Isolate the PaymentIDs to split → #PaymentIDsTBL

Only qualifying payments are collected: PayType='CAP', Status='OPEN', Method=@Method, having a CapVoucher in Fund1‑3 and also (via EXISTS) a CapVoucher in Fund4‑6 for the same PaymentID. So a payment is split only when it contains both weekly funds and withhold funds. DISTINCT means each PaymentID appears once here, no matter how many CapVoucher lines it has. 

-- qualifying filter (simplified)
SELECT DISTINCT p.PaymentID
FROM Payment p JOIN CapVoucher cv ON cv.paymentid = p.paymentid
WHERE p.PayType = 'CAP' AND p.Status = 'OPEN'
  AND cv.Method = @Method
  AND cv.FundID IN (@Fund1, @Fund2, @Fund3)              -- has a weekly fund
  AND EXISTS (SELECT * FROM capvoucher cv2
              WHERE cv2.FundID IN (@Fund4,@Fund5,@Fund6)   -- and a withhold fund
                AND cv.paymentid = cv2.paymentid)

3Outer loop — SUM the lines per fund → #PaymentTBL

This is the key collapse. For the current PaymentID (P0001), the 12 CapVoucher lines are aggregated with SUM(CAPAmount) grouped by fund (the query does not group by EnrollID). The two members' $500 lines per fund merge into $1,000 per fund, giving 6 rows — one per distinct fund. Each fund gets its week Description / CheckPrintBy label, and rows are ordered by Description, which sets the inner-loop order.

The first fund row keeps P0001. The procedure corrects the original Payment's amount from the $6,000 lump sum down to this fund's $1,000, stamps CheckPrintBy, and clears CheckAmt. No new PaymentID is created here.

CapVoucher / PayCheck rows for the first fund (both members' lines) are untouched — they already point at P0001, which now correctly represents just that fund's summed amount.

If the original amount had already equalled $1,000 (@@ROWCOUNT = 0), the procedure runs a second update that only sets CheckPrintBy and clears CheckAmt.

5Inner loops #2‑#6 — mint a new PaymentID per fund

For every fund after the first, a new PaymentID is generated from QCSIDB.dbo.IDSequence (idtype 4) via spQ_IDSeq. A new Payment row is inserted, then all of that fund's CapVoucher lines (both members), its PayCheck row (and CapAdjustment when applicable) are re-pointed from P0001 to the new PaymentID. Status = OPEN for weekly funds, WITHHOLD for withhold funds. 

INSERT INTO Payment (PaymentID, ..., Status, CheckPrintBy)
SELECT @NewPaymentID, ...,
   CASE WHEN @FundID IN(@Fund1,@Fund2,@Fund3) THEN 'OPEN'
        WHEN @FundID IN(@Fund4,@Fund5,@Fund6) THEN 'WITHHOLD' END, ...

UPDATE CapVoucher SET paymentid=@NewPaymentID WHERE PaymentID=@CurrentPaymentID AND FundID=@FundID;
UPDATE PayCheck   SET paymentid=@NewPaymentID WHERE PaymentID=@CurrentPaymentID AND FundID=@FundID;

7Notes — row counts, RECON / ADJUSTMENT & errors

How many rows does a PaymentID really have?

TableGranularityRows per PaymentID before split
Payment1 per PaymentIDExactly 1
CapVoucherper member (EnrollID) per fund per cap factorMany — (# members) × (# funds); not 6
PayCheckfund-level within the PaymentIDUp to # distinct funds (≤ 6)
#PaymentTBL (after SUM)1 per distinct fund= # distinct funds (≤ 6)

So the "6" only ever appears as the count of distinct funds after the group-by, and only when all 3 weekly + 3 withhold funds are present. Fewer funds → fewer resulting PaymentIDs.

RECON / ADJUSTMENT payments

The procedure runs for both MONTHLY and RECON cap types. When a PaymentID contains a CapVoucher with CapType = 'ADJUSTMENT' (a negative RECON amount), the procedure looks up the provider's ACTIVE, DIRECT affiliation into @NewPayToAffillID, uses it as the PayToAffilID for the adjustment rows so the negative amount can be absorbed, and re-points CapAdjustment rows to the new PaymentID along with CapVoucher/PayCheck.

Business rule: a negative RECON amount can never stand alone on its own PaymentID — it always stays attached to its associated FundID's PaymentID.

Error handling

The whole body is wrapped in TRY…CATCH; any failure is logged to dbo.SQLDEV_CAP_ERRORS (CAPType = 'Split Payment') with the error number, procedure, line and message — the run does not crash silently. 

INSERT INTO dbo.SQLDEV_CAP_ERRORS
  (CAPType, ErrorNumber, ErrorProcedure, ErrorLine, ErrorMessage)
VALUES ('Split Payment', Error_Number(), Error_Procedure(), Error_Line(), Error_Message());

Timing

Must run immediately after the Capitation run. The create-date filter was intentionally removed (per the 01/06/2023 change) because a CAP run can take up to 24 hours — so the procedure keys only off Status = 'OPEN'.
