1. Executive Summary

The Ohio CEF Capitation SSRS suite is a set of read-only operational and financial reports that render capitation payment data already produced by the QNXT/HealthPAS capitation runtime. Every report in scope is a thin SSRS shell over a single stored procedure that reads the authoritative capitation tables Plandata_Parallel.dbo.capvoucher and Plandata_Parallel.dbo.payment.

  • CONFIRMED Three of the four named reports exist in OH_FI_Reporting-main: FINRP00001, FINRP00001L, FINRP00001O. A fourth capitation report, CMS Capitation Summary, was discovered adjacent to them.
    Evidence: Financial/ folder listing — folders FINRP00001 - MCO Monthly Capitation Payment Cycle Totals, FINRP00001L - Capitation List, FINRP00001O - Capitation Operational Report, CMS Capitation Summary.
  • UNKNOWN FINRP00020 (“Monthly Counts & Detail”) does not exist in any repository searched. No RDL, dataset, or stored procedure by that identifier was found.
  • CONFIRMED All reports execute stored procedures (CommandType = StoredProcedure) against the shared data source HealthPAS_Reports — no embedded ad-hoc SQL in the RDLs.
  • INFERRED FINRP00001O is an operational supplement to the same MCO capitation payment data that EDI 820 generation consumes, but the report performs no programmatic reconciliation against EDI 820 output — it never reads the EDI staging tables.
  • CONFIRMED The capitation reports are pure downstream consumers. None writes back to capitation processing tables. The single write observed is FINRP00001O truncating/loading a reporting helper table HealthPAS_Reports.dbo.FIN1O_MCO_Medicaid_ID.

3. Report Architecture

The suite follows one consistent pattern. SSRS is a presentation layer only; all set logic lives in T-SQL.

Cross-cutting facts

  • CONFIRMED Reporting logic runs in SQL; SSRS only renders and applies =Sum(Fields!…) group/grand totals (FINRP00001 RDL L731-1059).
  • CONFIRMED Procedures live in the HealthPAS_Reports database but read cross-database from Plandata_Parallel (three-part names throughout each proc).
  • INFERRED The _Parallel suffix denotes a reporting replica/secondary of the transactional Plandata database; all reads use WITH (NOLOCK) / (nolock) hints, consistent with reporting off a replica.

4. FINRP00001 Analysis — MCO Monthly Capitation Payment Cycle Totals

Business purpose

CONFIRMED Produces per-provider (MCO/HMO) cycle totals of capitation for a paid-date window: non-adjustment, adjustment, withhold, total capitation payment, and member roster counts.

Evidence: proc select list sum(NonAdjustment) Non_Adjustment, sum(Adjustment) Adjustment, sum(WithHoldAmount) Withhold_Amount, sum(NonAdjustment + Adjustment) Capitation_Payment_Amount, max(distinct RosterCnt) Roster_Counts, max(RosterGrand) Roster_Grand — [dbo].[usp_MonthlyCapitationPaymentCycleCHIPtoMCOTotals].sql.

Parameters

  • @startdate / @enddate (smalldatetime) → SSRS params startdate / enddate. CONFIRMED RDL L22-27, params L1601-1607.
  • CONFIRMED Filter is on paydate between @startdate and @enddate (proc cteBase).

Classification logic (CONFIRMED)

  • NonAdjustment = captype='MONTHLY' AND fundid NOT LIKE 'WITH%' → capamount.
  • Adjustment = captype<>'MONTHLY' AND fundid NOT LIKE 'WITH%' → capamount.
  • WithHoldAmount = fundid LIKE 'WITH%' → capamount.
  • Roster = count(distinct carriermemid) per provider and grand total (cross apply).

Tables read

capvoucher a → payment b (a.paymentid = b.paymentid) → Enrollkeys m (carriermemid) → planprovinfo c (planprovid). CONFIRMED proc FROM/JOIN block.

INFERRED Despite the “CHIP to MCO” proc name, the report is scoped only by paydate and the fundid/captype classification — there is no explicit program filter in this proc, so it totals all capitation payments in the window grouped by payee provider.

5. FINRP00001L Analysis — Capitation List

Business purpose

CONFIRMED A member-level detail list of capitation payments with a derived Adjustment Reason for each row — the drill-down companion to the operational summary.

Evidence: header comment Description: Capitation List Report and the multi-stage temp-table build in [dbo].[usp_FINRP00001L_Capitation_List].sql; displayed fields include servicemonthyear, captype, capdate, capamount, amountpaid, paydate, memid, carriermemid, program, AdjustmentReason, provid, planprovid, npi, Line_of_Business (RDL L29-149).

Parameters

  • Active: @PaidBegDate, @PaidEndDate → SSRS paidbegdate/paidenddate (“Paid Beg/End Date*”). CONFIRMED RDL L17-20, L2311-2317.
  • CONFIRMED Many parameters (Program, PaymentType, MbrID, PaytoProvID, CapitationCode, ManagedCarePlanCode, AdjustmentReason…) exist in the proc but are commented out — the shipped report filters on paid-date only.

Adjustment-reason cascade (CONFIRMED)

Reason is resolved through a documented fallback chain, materialised across temp tables #temp_cappayments → #temp_planaction → #temp_cappayments_maxplanaction → …_planactionreasons → …_adjustmentreasons → …_Finaladjustmentreasons → …_Member:

  1. daycount = 0 → "Rate Change".
  2. Enrollment restriction with appcapitation='Y' → restriction description (restrictiontype).
  3. Membercondition cap factor → capitation code / description.
  4. planaction reason → action reason description; if multiple → enrollment change; if none → actiontype.
  5. memberpcp term/eff → "PCP Termination" / "Retro PCP Assignment"; else "Unknown".

Hard-coded scope & masking (CONFIRMED)

  • where p.checkprintdate >= '2023-02-01' — floor date embedded in proc.
  • and p.status in ('PAIDREMITP','PAIDREMIT') — only remitted/paid.
  • (Cv.CapType in ('RECON') or cv.capamount < cf.amount) — recon or below-factor rows.
  • top 200000 row cap on the member join.
  • VIP masking scaffolding present (svf_MaskType, isvip, *mask columns).

6. FINRP00001O Analysis — Capitation Operational Report

Business purpose

CONFIRMED By its own header it is "the Operational Report of Capitation List Report @ usp_FINRP00001L_Capitation_List" — an operational/summary presentation of the same capitation payment rows, scoped to managed-care programs, adding check number and withhold amount.

Evidence: header block and CREATE PROCEDURE [dbo].[usp_FINRP00001O_Capitation_Summary] in [dbo].[usp_FINRP00001O_Capitation_Summary].sql.

Parameters & lookup datasets

  • Main: @PaidBegDate, @PaidEndDate, @PaytoProvNPIID, @PaytoProvSortName, @PaytoProvExternalID. CONFIRMED RDL L64-76.
  • Two cascading lookup datasets: usp_Lookup_Line_of_Business and usp_Lookup_ProvSortName (fed by @NameSearch = Parameters!PaytoProvNameSearch.Value). CONFIRMED RDL L13-58.

Managed-care scope (CONFIRMED)

where p1.programid in ('PGMT00000000133','PGMT00000000132') and p.paydate between @PaidBegDate and @PaidEndDate and p.status in ('PAIDREMIT','PAIDREMITP','PAIDREMITA'). PGMT00000000133 resolves to "Medicaid Managed Care".

Evidence: program-id → label mapping when bp.programid ='PGMT00000000133' then 'Medicaid Managed Care' in Encounter/ENCRP00002 - Encounter Prompt Payment List/[dbo].[usp_ENCRP00002_Encounter_Prompt_Payment].sql L196.

Extra output columns vs. FINRP00001L (CONFIRMED)

  • p.checknbr as CheckNumber — rendered (RDL textbox CheckNumber, L1324-1342).
  • case when cv.fundid like '%withld%' then capamount else 0 end as WithholdAmount — rendered (RDL L1365).
  • top 10000 row cap on #temp_cappayments.

Side-effect write (CONFIRMED)

The procedure truncates and reloads a reporting helper table with the distinct MCO Medicaid IDs it produced:
truncate table [HealthPAS_Reports].dbo.FIN1O_MCO_Medicaid_ID then insert … select distinct planprovid from #temp_final.
Evidence: [dbo].[usp_FINRP00001O_Capitation_Summary].sql L395-396. No consumer of FIN1O_MCO_Medicaid_ID was found in any repository searched (see §8/§14).

12. Code-Level Findings

SSRS expression analysis (where calc happens)

  • CONFIRMED Aggregation is split: row-level sums/classification are in SQL; SSRS applies group + grand totals via =Sum(Fields!Non_Adjustment.Value), =Sum(Fields!Adjustment.Value), =Sum(Fields!Capitation_Payment_Amount.Value), =Sum(Fields!Withhold_Amount.Value) (FINRP00001 RDL L731-839 group, L951-1059 report totals).
  • CONFIRMED No custom <Code> block, RunningValue, or embedded VB was found in the capitation RDLs; all business logic is T-SQL.
  • INFERRED VIP masking is intended to be an SSRS-visible column set (*mask fields), driven by member.isvip and svf_MaskType('Text') in the proc (FINRP00001O IIF-based masking; FINRP00001L exposes both masked and clear columns).

Performance observations

  • CONFIRMED FINRP00001L / FINRP00001O build long temp-table chains (7+ #temp_* tables) with select distinct at each stage — repeated large scans of capvoucher/payment.
  • CONFIRMED Row caps in place: FINRP00001L top 200000; FINRP00001O top 10000 on #temp_cappayments. These bound output but can silently truncate large windows.
  • CONFIRMED Correlated max(effdate) subqueries on memberpcp executed per row of the PCP resolution (FINRP00001L/001O).
  • CONFIRMED FINRP00001O creates a nonclustered index on #memcond to mitigate the membercondition join.
  • CONFIRMED All source reads use NOLOCK; acceptable on a reporting replica but risks dirty reads if pointed at a live DB.

Data-quality / correctness notes

  • CONFIRMED FINRP00001L embeds a hard floor p.checkprintdate >= '2023-02-01' in addition to the paid-date parameters — results before Feb-2023 are impossible regardless of parameter input.
  • CONFIRMED Withhold detection differs between reports: FINRP00001 uses fundid LIKE 'WITH%'; FINRP00001O uses fundid like '%withld%'. Divergent string patterns risk inconsistent withhold totals across the suite.
  • INFERRED FINRP00001O suppresses the planaction date window (createdate between cap/pay date) with a comment “SUPPRESSED THE DATE FOR TESTING IN E2E Need to confirm on PROD”, so its adjustment-reason resolution may differ from FINRP00001L in production.

Security analysis

  • CONFIRMED Application-level masking of VIP members via member.isvip + svf_MaskType (FINRP00001O / 001L).
  • UNKNOWN SSRS folder/role security and report-level permissions are not expressed in the RDLs and no SSRS policy export was found in these repos — requires the SSRS catalog to confirm.

16. Final Verdict

  1. What does FINRP00001 actually report? Per-payee (MCO/HMO provider) monthly capitation cycle totals for a paid-date window — non-adjustment, adjustment, withhold, total capitation, and distinct member roster counts. CONFIRMED (proc sum/classification; RDL Sum totals).
  2. What does FINRP00001L actually report? A member-level Capitation List (detail) of paid/remitted capitation vouchers with a derived Adjustment Reason via a restriction→condition→planaction→PCP cascade. CONFIRMED.
  3. What does FINRP00001O actually report? The operational summary of the Capitation List, scoped to managed-care programs (133/132), additionally exposing check number and withhold amount; it stages distinct MCO Medicaid IDs into FIN1O_MCO_Medicaid_ID. CONFIRMED.
  4. Does FINRP00001O support EDI 820 reconciliation? It supplements, it does not reconcile. It reports the same MCO capitation payments the 820 pipeline consumes, but performs no join to, read of, or comparison against EDI 820 staging/output. INFERRED supplement / CONFIRMED no EDI table access.
  5. What does FINRP00020 actually report? Unknown — no such artifact exists in the workspace. UNKNOWN.
  6. Which stored procedures drive each report? FINRP00001→usp_MonthlyCapitationPaymentCycleCHIPtoMCOTotals; FINRP00001L→usp_FINRP00001L_Capitation_List; FINRP00001O→usp_FINRP00001O_Capitation_Summary (+ lookups); CMS→usp_CMS_Capitation_Summary. CONFIRMED.
  7. Which tables are authoritative sources? Plandata_Parallel.dbo.capvoucher joined to Plandata_Parallel.dbo.payment are the authoritative capitation-payment sources for every report. CONFIRMED.
