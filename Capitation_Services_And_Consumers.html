Capitation Services & Where They Are Consumed

Repository: act-OH-FIWebSvc-main  |  Ohio FI (Fiscal Intermediary) Web Services

Answer: Yes. Capitation is handled in this repo through the CapVoucher (capitation payment voucher) that flows out of the PaymentInquiry / GetPaymentDetails SOAP operations. Capitation is a payment model where a provider is paid a fixed periodic amount per member. Below are the capitation-bearing services, the end-to-end data flow, and every project/process that consumes them. There are also generated VUE360 capitation client operations that are declared but not called.

1. Services / APIs that produce capitation data

Gainwell.FI.SOAPService — primary capitation output Live

This is the primary place capitation vouchers are produced and returned to callers.

The implementation calls IPaymentInquiryService.PaymentInquiry() and maps results via PaymentDataMapper.ConvertStructure(), returning capitation payment inquiry data to the IVR/telephony channel.

2. CapVoucher data flow (end to end)

  1. Caller (IVR / EDI Gateway / internal) sends a PaymentInquiry (PaymentID, EnvironmentID).
  2. PaymentInquiryQuery (MediatR query object) Applications/Queries/PaymentInquiryQuery.cs
  3. PaymentInquiryHandler.Handle() enriches the query and delegates Applications/QueryHandlers/PaymentInquiryHandler.cs
  4. FinanceServiceController.GetPaymentDetails() calls mHPServicesClient.GetPaymentDetailsAsync(PaymentID, envID) ModularServices/FinanceServiceController.cs
  5. MHPServicesClient (WCF proxy to MyHealthPAS back-end) returns MHPServices.PaymentDetails containing CapVoucher[] ServiceRepository/Connected Services/MHPServices/Reference.cs (auto-generated)
  6. AutoMapper — PaymentInquiryProfile maps MHPServices.CapVoucher → Entities.CapVoucher Applications/AutoMappingConfig/PaymentInquiryProfile.cs
  7. PaymentInquiryResponse.CapVoucher returned to the caller Applications/ClientResponses/PaymentInquiryResponse.cs

CapVoucher fields: FullName, CapType, DayCount, CapDate, CapAmt. Defined identically in three layers: FI SOAP service (Applications/Entities), HPO SOAP service (Applications/FIModel), and MyHealthPAS proxy (Applications/Entities).

Summary
  • Active capitation service: the PaymentInquiry / GetPaymentDetails operation returns capitation vouchers (PaymentInquiryResponse.CapVoucher), sourced from the MyHealthPAS back-end.
  • Live consumers: Gainwell.FI.SOAPService (producer), Gainwell.HPO.SOAPService (IVR-facing), and MyHealthPAS.SOAP.Proxy (delegating bridge).
  • Inactive consumers: Gainwell.IVR.WCFServices uses mock data; HPO.IVR.WCFService and Gainwell.InternalIVR have their integration commented out/disabled.
  • Declared-but-unused: the five VUE360 capitation client operations exist only in generated proxy code and are not invoked anywhere in this repo.
  • No capitation UI lives here — the capitation screens are in the mms-cms-v360-main (VUE360) repository.
