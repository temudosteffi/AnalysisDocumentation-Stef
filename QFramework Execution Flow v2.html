QFramework / QEnterprise — Capitation Execution Flow v2

Focus of this version: how a message/transaction is identified, picked, and routed to a specific Execution Unit, and how that EU uses the ID to retrieve the payload from the Message Store and process the work. Every claim is cited from source under mms-cms-cef/components/QFrame.

The one idea to hold onto: the hub never sends the data. It sends a message ID string (the QISMessageId). The EU receives that ID, takes ownership of that exact row in the Message Store, and loads the payload from the database by that ID. Identification happens on three keys: the QISMessageId (which record), the LogType (which EU can handle it), and ownership / QnxtServerId (which server owns it right now).

0. Identifiers & Components at a Glance

QISMessageId

the record key
a string ID (Message Store message.messageid, char(36)). This is what is sent to the EU.

LogType

the routing key
e.g. ADV_CAP_PROC. Decides which EU is allowed to process the message.

QnxtServerId / ownership

the claim key
stamps which server owns the row so two servers never grab the same message.

EU address (URI + port)

the destination
RemotingURI + RemotingPort — how the hub reaches the chosen EU.

The identifiers moving through the pipeline

 client ── message + LogType ──▶  DISTRIBUTION HUB
                                   │  1. PersistMessage → gets QISMessageId, saved in Message Store (state = DistributionHubCache)
                                   │  2. aMessage.Message = null           ◀ drop the payload from memory (claim-check)
                                   │  3. route by LogType → QueueReader[LogType]
                                   │  4. match LogType → an ACTIVE EU (AcceptedMessageTypeCol) ; round-robin ; honor MaxOutstandingRequests
                                   │  5. GetRemotingRef(URI:port) ; state → Transit
                                   ▼  BeginInvoke( QISMessageId )           ◀ ONLY the id is sent
                              EXECUTION UNIT
                                   │  6. loadMessageObjectFromDB(QISMessageId)
                                   │     → TakeOwnershipOfMessageAndGetMessageInfo(id)   ◀ claim + fetch payload by id
                                   │  7. state → Executing ; run on thread pool
                                   ▼
                        MessageProcessorEngine → CapProgramAgent (ADV_CAP_PROC)
                                   │  8. success → RemoveMessage(QISMessageId) ; state → Complete

1. SETUP — The Hub Learns LogTypes & the EUs Register

Step 1Distribution Hub/MessagPort.cs · Main.cs

1.1 The hub builds one queue per LogType — read from the database

At startup the hub asks the Message Store which process LogTypes exist (the messagetype table) and creates one QueueReader per type. This is the master list of routable message types.

QFrame/Infrastructure/Common/Src/WindowsService/Distribution Hub/MessagPort.cs — static QISDistributionHub()
// one QueueReader per message type that the DH will handle,
// read directly from the messagetype table in the message store database
DataTable dt = QISDistributionHubService.QIS.MessageStore.GetProcessLogTypes();
if (dt.Rows.Count == 0)
    throw new Exception("Distribution hub is not configured with any process log types in message store database.");

LogTypes = new string[dt.Rows.Count];
for (int i = 0; i < dt.Rows.Count; i++)
{
    LogTypes[i] = dt.Rows[i][0].ToString().Trim();
    QueueReaderCol.Add(LogTypes[i], new QueueReader(LogTypes[i]));   // keyed by LogType
}

1.2 Each EU registers which LogTypes it accepts + its address

For every EU, the hub reads QISConfig.xml and records: the LogTypes it accepts (into AcceptedMessageTypeCol), the connect method (Remoting TCP/HTTP), and the EU's port + URI. That URI/port is the address the hub will dial later.

.../Distribution Hub/Main.cs — EU load loop
// which process log types can this EU process
foreach (XmlNode aMessage in EUConfig.SelectNodes("//Messages/Message"))
    aUnit.AcceptedMessageTypeCol.Add(((XmlElement)aMessage).GetAttribute("LogType"), "ACCEPT");

switch (aNode.SelectSingleNode("@ConnectMethod").Value)
{
  case "REMOTING":
    switch (aNode.SelectSingleNode("@ConnectChannel").Value)
    {
      case "TCP":
        aUnit.ConnectMethod = QISConnectMethod.REMOTING_TCP;
        aUnit.RemotingPort  = Convert.ToInt32(EUConfig.SelectSingleNode("//ExecutionUnit/@TCP_PORT").Value);
        aUnit.RemotingURI   = EUConfig.SelectSingleNode("//ExecutionUnit/@URI").Value;   break;
      case "HTTP":
        aUnit.ConnectMethod = QISConnectMethod.REMOTING_HTTP;
        aUnit.RemotingPort  = Convert.ToInt32(EUConfig.SelectSingleNode("//ExecutionUnit/@HTTP_PORT").Value);
        aUnit.RemotingURI   = EUConfig.SelectSingleNode("//ExecutionUnit/@URI").Value;   break;
    }
}
aUnit.StartHeartBeat();                 // liveness monitor → sets Active / Dead
aUnit.ArrayIndex = ExecutionUnits.Count;
lock (ExecutionUnits) { ExecutionUnits.Add(aUnit); }   // the EU registry (round-robin list)
After setup the hub holds: a QueueReaderCol keyed by LogType, and an ExecutionUnits list where each EU knows which LogTypes it accepts and how to be reached (URI:port).

2. INTAKE — A Message Arrives, Gets an ID, and Is Stored

Step 2Distribution Hub/MessagPort.cs

A client calls the hub's remoting endpoint IQISDistributionHub.ApplicationMessage(...). The hub persists the message to the Message Store — this is where the QISMessageId becomes the durable key — then drops the payload from memory and routes the lightweight message object (now just metadata + ID) to the matching per-LogType queue.

.../Distribution Hub/MessagPort.cs — SubmitToQueue()
internal void SubmitToQueue(CQISMessage aMessage, bool ThrowError)
{
    // 1) persist the full message (payload) to the Message Store with a state
    QISDistributionHubService.QIS.MessageStore.PersistMessage(aMessage, QISMessageState.DistributionHubCache);

    // 2) the in-memory copy no longer needs the payload — only the id/metadata travels now
    aMessage.Message = null;                                   // ◀ claim-check begins here

    // 3) hand the message to the queue for its LogType
    ((QueueReader)QueueReaderCol[aMessage.LogType]).RouteMessage(aMessage);
    Interlocked.Increment(ref QISDistributionHubService.QIS.QueueTx);
}
Where the ID comes from: the identifier is the Message Store key message.messageid (a char(36) value), surfaced on the in-memory object as aMessage.QISMessageId. From this point on, that string is the message — everything else references it.

3. IDENTIFY — Pick the Right Execution Unit

Step 3Distribution Hub/MessagPort.cs — QueueReader.DoReader()

The queue reader for a LogType dequeues a message and must choose an EU. Two gates decide identification: (a) the EU must accept this LogType, and (b) the EU must be active. The hub round-robins (CurrentUnit) so load spreads across all capable EUs.

.../Distribution Hub/MessagPort.cs — QueueReader.DoReader()
// (a) make sure at least one EU can consume this LogType, else release it back to the store
bool foundEU = false; int searchUnit = 0;
while (!foundEU)
{
    QISExecutionUnit unit = (QISExecutionUnit)QIS.ExecutionUnits[searchUnit];
    if (unit.AcceptedMessageTypeCol.ContainsKey(aMessage.LogType)) { foundEU = true; break; }   // ◀ LogType match
    if (++searchUnit >= QIS.ExecutionUnits.Count)
    {   // nobody can handle it → return to Message Store, release ownership
        QIS.MessageStore.ResubmitMessage(aMessage.QISMessageId, false);
        break;
    }
}

// (b) round-robin to the next ACTIVE, capable EU
QISExecutionUnit aUnit = (QISExecutionUnit)QIS.ExecutionUnits[CurrentUnit];
foundActiveEU = aUnit.Active;                                   // ◀ liveness gate (heartbeat)
if (!aUnit.AcceptedMessageTypeCol.ContainsKey(aMessage.LogType)) { CurrentUnit++; /* try next */ }
...
if (aUnit.RouteMessage(aMessage)) { /* handed to that EU's send queue */ }
Back-pressure: each EU has MaxOutstandingRequests (code default 2, set per-EU in config). If an EU already has that many in flight (m_outstanding > m_maxoutstanding), the hub skips it and tries the next — so a busy EU is never overloaded.

4. SEND — Only the QISMessageId Crosses the Wire

Step 4Distribution Hub/ExecutionUnit.cs — RemotingRequestState.StartRequest()

The hub gets a live remoting reference to the chosen EU (dialing its RemotingURI:RemotingPort), marks the message Transit in the store, and asynchronously invokes the EU's ApplicationMessage passing only Data.QISMessageId.

.../Distribution Hub/ExecutionUnit.cs — RemotingRequestState.StartRequest()
IQISExecutionUnit aUnit = ((QISExecutionUnit)QIS.ExecutionUnits[ParentKey]).GetRemotingRef();  // connect to EU URI:port
AMD = new ApplicationMessageDelegate(aUnit.ApplicationMessage);

QIS.MessageStore.StateChangeSingleMessage(Data.QISMessageId, QISMessageState.Transit);         // mark in-flight
Result = AMD.BeginInvoke(Data.QISMessageId, out AsyncResponse, new AsyncCallback(GetResponse), this);
//                        ▲ the ONLY thing sent to the EU is the message-id string
// on any transport error → QIS.MainHub.SubmitToQueue(Data);  (re-queue for another EU)

5. RECEIVE — The EU Loads the Payload by ID (Takes Ownership)

Step 5Execution Unit/MessagePort.cs

The EU exposes a remoting object. Its ApplicationMessage(string Request, …) receives the ID. The method's own XML doc comment states the contract: "Unique message id that points to the record in message store database." It then loads that record by ID, validates the environment, flips state to Executing, and queues the work on a thread pool.

Execution Unit/MessagePort.cs — QISExecutionUnit.ApplicationMessage(string Request, …)
/// <param name="Request">Unique message id that points to the record in message store database</param>
public bool ApplicationMessage(string Request, out string Response)
{
    // fetch the whole message (payload) from the Message Store using the id
    CQISMessage msgObject = loadMessageObjectFromDB(Request);

    // ... validate the environment the message belongs to ...

    Processed.Add(msgObject.QISMessageId, msgObject.QISMessageId);
    QIS.MessageStore.StateChangeSingleMessage(msgObject.QISMessageId, QISMessageState.Executing);   // state → Executing

    m_pool.ProcessItem(new ThreadStart((new Worker(msgObject)).ProcessTX));   // run the work on a pool thread
    Response = "PROCESSING";
    return true;
}

5.1 The fetch-by-ID itself (claim + load in one call)

This is the literal "retrieve the payload from the message store" by ID. The method TakeOwnershipOfMessageAndGetMessageInfo(msgId) both claims ownership of that row and returns its data; the row is then turned into the message object (payload included).

Execution Unit/MessagePort.cs — loadMessageObjectFromDB()
private CQISMessage loadMessageObjectFromDB(string msgId)
{
    DataTable dt = QISExecutionUnitService.QIS.MessageStore.TakeOwnershipOfMessageAndGetMessageInfo(msgId);  // claim + fetch by id
    if (dt.Rows.Count == 0)
        throw new Exception("Message with id: " + msgId + " does not exist in message store");
    return CQISMessageHelper.CreateFromDataRow(dt.Rows[0]);     // DataRow → message object (payload)
}
Answer to "how are messages identified / picked at the EU": the EU is handed the QISMessageId string over remoting. It calls TakeOwnershipOfMessageAndGetMessageInfo(id), which looks the record up by that exact id in the Message Store, takes ownership of it, and returns the row — from which the payload is rebuilt. No scanning, no guessing: a direct key lookup on the id the hub chose.

6. PROCESS — The Engine Runs the Capitation Agent

Step 6Execution Unit/MessagePort.cs — Worker.ProcessTX() · QCSI Process Execution

The thread-pool worker selects the message's environment, logs ERS_EXECUTE, and runs the QFramework engine over the message body. The engine looks up the process for the message's LogType (e.g. ADV_CAP_PROC) and invokes the capitation agent.

8. How Message IDs Are Identified & Routed — Summary

QuestionAnswer (from code)
What is the message's identity?The QISMessageId string = the Message Store key message.messageid (char(36)), created when the hub calls PersistMessage.
How does the hub decide which EU gets it?By LogType: aUnit.AcceptedMessageTypeCol.ContainsKey(aMessage.LogType), among Active EUs, chosen round-robin (CurrentUnit), skipping any EU at its MaxOutstandingRequests.
How is the EU reached?The hub dials the EU's RemotingURI + RemotingPort via GetRemotingRef() (TCP or HTTP remoting).
What is actually sent to the EU?Only the id: AMD.BeginInvoke(Data.QISMessageId, …). The payload is not sent (it was dropped from memory at intake).
How does the EU get the payload?loadMessageObjectFromDB(id) → TakeOwnershipOfMessageAndGetMessageInfo(id) — a direct key lookup that also claims ownership, then CQISMessageHelper.CreateFromDataRow rebuilds the payload.
How are duplicates prevented?Ownership: a server stamps the row (QnxtServerId) and advances its state (Transit → Executing); another server/DH ignores rows it does not own.
How does the EU signal done?RemoveMessage(QISMessageId) deletes the row (ack); failures use StateChangeSingleMessage(id, Error) or re-queue.
