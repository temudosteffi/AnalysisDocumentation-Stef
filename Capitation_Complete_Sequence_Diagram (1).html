Description — Stage 0 (Run Invocation):
  • Entry Point: QNXT Administrator clicks "Create Capitation Payments" wizard (3-step UI in QNXTALL.sln).

Description — Stage 1a (Enrollment Build):
  • Purpose: Answers "Who is on the payroll this month?" — builds the roster of members eligible for capitation for a given provider/program/month.
  • Entry Point: CapitationActivity.BuildCapEnrolls(message) → creates cBuildCapEnrolls instance.

Description — Stage 1b (MCO-Assignment Resolution):
  • Purpose: Answers "Which department does each person's salary get charged to?" — resolves the chain: Member → MCO Assignment → Provider Contract → Capitation Table → Rate.
  • Entry Point: CapitationActivity.SelectCapAffiliations(message) → creates cBuildCapAffils.
  • Key Operations: (1) Load rate codes from enrollcoverage, (2) Load policy copays, (3) Resolve contract→cap table linkage via Query 10978, (4) Build month-by-month schedule with eligible days, (5) Apply carve-outs and enrollment restrictions.

Stage 4 — Fund Allocation & Winner Selection

Figure 5: Stage 4 — 10-Dimension Rate-Cell Winner Selection (Query 10794)
sequenceDiagram

    participant Plandata as Plandata_Parallel DB

    Stage3->>Stage4: CapitationActivity.AllocateCapFunds(message)
    Stage4->>Stage4: Compute current_age = DateDiff(Month, DOB, capdate)
    Note over Stage4: Age in MONTHS not years! (360 = 30 years, sentinel 1320 = 110yrs)
    Stage4->>Stage4: Build policycopaygroupselect SQL fragment
    Stage4->>Stage4: Build servicezipwhere clause (PCP service ZIP)
    Stage4->>Plandata: Query 10794: SELECT matched, possible, capterm.*
    Note over Plandata: FROM capitation JOIN capterm WHERE capid=@capid AND effdate/termdate
    Plandata-->>Stage4: Candidate rate cells with matched/possible scores
    Stage4->>Stage4: Sort: possible DESC, matched DESC, agemax ASC, agemin ASC, capamount DESC
    Stage4->>Stage4: Accept FIRST row where matched = possible AND matched > 0
    Note over Stage4: Winner = most specific cell satisfying ALL defined criteria
    loop For each winning capterm (per fund)
        Stage4->>Plandata: WriteFundDetail() → INSERT funddetail (startamt, endamt)
    end
    Note over Stage4: Output: captermid + fundid + startamt per affiliation/month
Description — Stage 4 (Fund Allocation & Winner Selection):
  • Purpose: Selects the single best-matching rate cell from all candidate capterm rows using a 10-dimension scoring algorithm, then allocates the amount across configured funds.
  • Entry Point: CapitationActivity.AllocateCapFunds(message) → creates cCapFundAllocation.
  • Winner Selection Rule: A rate cell is valid if and only if matched = possible — the member must satisfy EVERY criterion the cell defines.
  • 10 Scoring Dimensions: ZIP, ratecode, gender (sex), agemin, agemax, planid, copaygroupid, copayid+copayamt (paired).
  • Tie-Break Sort: "possible DESC, matched DESC, agemax ASC, agemin ASC, capamount DESC" — narrower age ranges (more specific) win.
  • CRITICAL: Age is in MONTHS (not years). A reimplementation using years will select wrong rate cells and pay wrong amounts.
  • DB Tables: READ: capitation, capterm (Query 10794). WRITE: funddetail (INSERT with startamt).
  • .sln: QCSI ASC Capitation.sln (cCapFundAllocation.vb), QCSI Access Payment.sln (10794.xml).

    Stage4->>Stage5: CapitationActivity.AdjustCapFunds(message)
    Stage5->>Plandata: Query 87: capfactors JOIN factorvalues JOIN factortypes
    Plandata-->>Stage5: All cap factors for this cap arrangement

    end
    loop For each matching factor
        Note over Stage5: AGE/GENDER | BENEFIT PLAN | RATE CODE | CONDITION
        Stage5->>Stage5: If amounttype=P: (amount/100) x startamt, else flat $
        Stage5->>Stage5: endamt = endamt + adjustment (ADDITIVE composition)
        Stage5->>Plandata: Query 131: UPDATE funddetail SET endamt=@endamt
        Stage5->>Plandata: Query 138: INSERT funddetailadj (audit record)
    end
    alt capmethod = S
        Stage5->>Stage5: PayBySplitmonth() — split at configured day
    else capmethod = F
        Stage5->>Stage5: PayByFrontEndBackEndWash() — zero if past midpoint
    else default
        Stage5->>Stage5: AdjustForDays() — pro-rate by enrolled days
    end
    Note over Stage5: Output: final adjusted endamt per fund
Description — Stage 5 (Cap Factor Adjustments):
  • Purpose: Takes the base amount from Stage 4 and applies configured adjustments, then handles special payment methods (split-month, front/back wash, true-cap pro-ration).
  • Entry Point: CapitationActivity.AdjustCapFunds(message) → creates cCapFundAdjustment.
  • Factor Composition: Factors are ADDITIVE — each factor's percentage is applied against the original startamt (not accumulated endamt), then added to the running total.
  • Four Factor Types: AGE/GENDER (minval/maxval + sex B/M/F), BENEFIT PLAN (planid), RATE CODE (rateid + ratecode list), CONDITION (active membercondition).
  • Cap Methods: "S" = split month at splitmonthday with firsthalfpercent/sechalfpercent, "F" = zero if PCP effective after midpoint or term before midpoint, default = true-cap pro-ration by days.
  • DB Tables: READ: capfactors, factorvalues, factortypes (Query 87), membercondition (Query 86). WRITE: funddetail (UPDATE endamt), funddetailadj (INSERT audit).
  • .sln: QCSI ASC Capitation.sln (cCapFundAdjustment.vb).

Description — Stage 7 (Write Layer):
  • Purpose: The point where computed amounts become permanent database records. Two sub-steps: (1) cStoreCapVoucher writes individual voucher rows, (2) cCapPayment aggregates into the final payment.
  • Fan-In: N member-level capvoucher rows roll up into 1 payment per pay-to affiliate (inverse of Stage 0 fan-out).
  • capvoucher PK (13 columns): paymentid, captype, caprateid, captermid, capmonth, affiliationid, enrollid, fundid, paytoaffilid, networkid, recondate, factorvalueid, capadjustmentid.
  • CRITICAL RISK: Bare INSERT, NO transaction, NO MERGE/upsert, NO scope-clear. Restart reuses original paymentid → PK violation. Production evidence: 153,071 collisions per RECON run.
  • Finalization: Waits for all batches, deletes $0 vouchers, aggregates by fund, creates paycheck, sets payment.status='OPEN'.
  • DB Tables: R/W: capvoucher, payment, paycheck, pooltrans, funddetail/funddetailadj, capmessagequeue, capadjustment.
  • .sln: QCSI ASC Capitation.sln (cStoreCapVoucher.vb, cCapPayment.vb).

Description — Stage 8 (PlanIntegration) & Stage 9 (QCSIDB):
  • PlanIntegration (Stage 8): The "control tower" — 192 process chains, 214 agents, ~2B rows in processstate. At dispatch, ProcessManager reads process → processstep → agent to resolve which .NET assembly to load.
  • CRITICAL: processstate is NOT a serialization lock. It only records what happened AFTER the fact. Nothing prevents concurrent runs for the same scope.
  • QCSIDB (Stage 9): COTS engine infrastructure (38 tables). Primary function: centralized ID generation via spQ_IDSeq (~430 lines T-SQL). 80+ ID types. 12 of 17 repos consume it.
  • ID Serialization: UPDATE idsequence SET rawval += @iterations WHERE idtype=@idtype acquires exclusive row lock. All ~71 concurrent cap runs serialize through idtype=4.
  • Capitation Chains: ADV_CAP_PROC (program), ADV_CAP_BATCH (batch + inactive PostCap), CapProvProc (provider), CapReStartProc (restart).
  • DB Tables: PlanIntegration: process, processstep, agent (READ), processstate, processlogheader/detail (WRITE). QCSIDB: idsequence (UPDATE), dbalias, envconfig (READ).
  • .sln: QCSI Process Execution, QCSI IDSequence LDL.sln, QCSI Process Log.sln, DistributionHub.sln.

Description — Post-Cap (Fund Allocation + Split Payment):
  • Purpose: Ohio-custom processing after cap engine. (1) Classify vouchers for GL fund allocation, (2) Split payments across weekly distribution funds.
  • Trigger: PostCapitationFundAllocationAgent / PostCapitationSplitPaymentAgent (ADV_CAP_BATCH steps 1-2 are INACTIVE — actual trigger unknown).
  • PostCap_PreFundAllocate: Joins 10+ Plandata tables + HealthPAS_Common, assigns RCGroup (1-5) via CAPRateExtensions, determines RateCodeExtn, INSERTs into hpfin_FAAttributesCAP.
  • PostCap_SplitPayments: For each OPEN cap payment, generates NEW paymentid(s) via spQ_IDSeq, creates new payment rows, reassigns capvoucher/paycheck to new IDs.
  • RISK: PostCap directly modifies capvoucher.paymentid — concurrent restart = data corruption.
  • DB Tables: READ: capvoucher, payment, enrollkeys, membercondition (Plandata); ELGIP00005_SUPP_GAP (HPC). WRITE: hpfin_FAAttributesCAP (HPC); payment, capvoucher, paycheck (Plandata).
